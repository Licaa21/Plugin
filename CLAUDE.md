This folder is the **implement** branch.

## Read this first

Personal fork of the Moonfin server plugin (Moonbase, for Jellyfin 10.10+) by Moonfin-Client (RadicalMuffinMan and the contributors). The fork is Licaa21/Plugin and holds changes for one person's own server. It is not a project for everyone. It exists so that the Moonfin Smart TV fork (Licaa21/Smart-TV, a Samsung Tizen and LG webOS app, kept in `E:\VSCode Projects\Moonfin Smart TV fork`) needs no TMDB key of its own: the plugin holds the server-wide TMDB key and serves the TMDB words, recommendations and air dates the client used to fetch itself. The fork replaces the upstream plugin in place: same GUID (`8c5d0e91-4f2a-4b6d-9e3f-1a7c8d9e0f2b`) and name (Moonbase), so the saved settings stay, and Jellyfin offers it from the fork's own manifest.

1. Upstream moves. In `main/`: `git fetch upstream`, then `git merge upstream/master`. A conflict is fixed in `main/` and committed there (see the merge checklist), then `implement` takes it with `git merge origin/main`, so the resolution is not redone. `main` is never rewritten.

## What the TV client expects

The TV fork (Licaa21/Smart-TV, app code in `packages/app/src`) used to ask TMDB itself with its own key (`utils/tmdbText.js`, `utils/seerrTitle.js`, `utils/seerrSeasons.js`, `services/homeRecommendations.js`, `utils/upcomingEpisode.js`). It is changed to call the plugin once these routes exist, and to fall back to Seerr's own text when a route answers with anything but 200. The key is the plugin's server-wide `TmdbApiKey` (`PluginConfiguration.TmdbApiKey`), never a per-user key and never sent to a client.

All routes are under `Moonfin/Tmdb`, `GET`, `[Authorize]` like the others, and answer JSON with **TMDB's own snake_case field names**, so the client can use them as it used TMDB's. Parameters: `tmdbId` (TMDB id), `mediaType` (`movie` or `tv`), `language` (as the existing `Reviews` route takes it, run through the same `TmdbReview.RequestLanguage`, empty meaning `en-US`). Any non-200 answer means "use Seerr's text".

| Route | Answers |
|---|---|
| `Details?mediaType=&tmdbId=&language=` | `{id, title, name, original_title, overview, tagline, seasons: [{season_number, name}], next_episode_to_air: {season_number, episode_number, air_date, name} or null}`. A movie has no `seasons` and no `next_episode_to_air`. |
| `Season?tmdbId=&seasonNumber=&language=` | `{season_number, name, overview, episodes: [{season_number, episode_number, name, overview, air_date, runtime, still_path, vote_average, vote_count, crew, guest_stars}]}`. `crew` and `guest_stars` come through as TMDB gives them. |
| `Recommendations?mediaType=&tmdbId=&language=&page=1` | `{page, total_pages, results: [...]}` with TMDB's result objects as they are. |
| `NextEpisode?tmdbId=` | Exists already, unchanged. The client uses it for the air date. |

Errors: 400 for a missing or bad parameter, 503 when the server has no TMDB key (with `{error}` that does not mention the key), 404 when TMDB does not know the id, 502 when TMDB fails or answers something that is not TMDB's. Nothing of the key in any body, header or log line. Answers are remembered in memory for 24 hours per route, ids, season, language and page (as `TmdbController`'s caches already do), with a ceiling on the number of entries so memory cannot grow without end.

**Built and released as 2.4.0.1** (2026-10-25, tag `fork-v2.4.0.1`, built from `main` 32769d2; the zip's MD5 from GitHub matched the manifest; installing it and checking the routes on the real server is still to be done): `Jellyfin/backend/Services/TmdbProxyService.cs` holds the logic and the caches, and `TmdbController` has the three thin actions `GetDetails`, `GetSeason` and `GetRecommendations`, which hand it `CreateClient()` and the server-wide key (`ServerApiKey()`, never `GetUserApiKey()`). Exact behaviour, where the table above leaves it open:

- `Details` returns only the listed fields. A movie answers `id`, `title`, `original_title`, `overview`, `tagline` (whichever TMDB sent); a series answers `name` instead of `title`, `seasons` (every season TMDB lists, specials included) and `next_episode_to_air`, which is `null` when nothing is scheduled. An empty translation stays empty: there is no second call in English, so the client falls back to Seerr's text itself.
- `mediaType` is `movie` or `tv` (any case), `tmdbId` a positive whole number, `seasonNumber` a whole number from 0, `page` 1 to 500 (a missing or blank page is 1). The service reads all of them as text, so a non-number gets the `{"error": ...}` 400 too, not the framework's own. Anything else is 400, before any TMDB call and before the key is looked at.
- Errors are `{"error": "..."}` (lower case, whatever the host's JSON naming). 404 when TMDB says 404; 502 for any other TMDB failure (401, 429, 5xx, timeout, network) and for a 200 that is not the right shape (not an object, no `id`, no `episodes` or `results` array, wrong-typed elements).
- Answers are written with relaxed JSON escaping, so non-English text is not turned into `\uXXXX` escapes. One cache per route, 500 entries each, 24 hours; when full, expired entries go first and then the oldest. Only 200 answers are cached.
- The only log lines are the route name and TMDB's status code or the exception type, never an address.
- Not checked against the real server or the TV app: it needs the key and an installed build.

**Known limits, accepted by the user on 2026-10-25** (do not "fix" these without asking):

- The cache ceiling counts entries, not bytes. A `Season` answer with every crew and guest-star list can be a few hundred KB, so a full `Season` cache can hold tens of MB or more.
- Concurrent misses on one key are not merged: several clients asking for the same uncached title each call TMDB.
- Only 200 answers are cached. A 404, 429 or 5xx is asked again every time, and there is no per-user rate limit, so any signed-in user can use up the server key's TMDB quota.
- A v3 TMDB key travels in the request URL (`api_key=`), so the host's own `System.Net.Http.HttpClient` logging would print it if someone turned it up to Information. The older routes have the same exposure; v4 tokens go in a header and are not affected.
- The cache drops the oldest entry, not the least recently used.
- A TMDB 401 (a wrong or revoked server key) comes back as the same 502 as an outage and is asked again every time; the only trace is a warning in the log with the status code. A language code that is not in the exact form `xx` or `xx-YY` (so `en-us` too) is not an error, it is read as `en-US`.
- `language` is only checked for the shape `xx` or `xx-YY`, not against the languages TMDB has, so a caller can make many cache keys for one id (the same quota and eviction effect as the points above).
- **Push notifications:** upstream's builds embed the key for Moonfin's hosted push relay (`push.moonfin.io`); the fork's public zip cannot, so `PushEnabled` is false and nothing is pushed to phones whose Moonfin app is closed. The maintainer was asked on 2026-10-25 and said no to sharing the key (upstream's wiki says to run your own Firebase project and set the *Push Service Account* or *Push Service Account File Path* in Moonbase). That is the only route; it may not reach the App Store version of Moonfin on iOS, whose push tokens belong to Moonfin's own Firebase project (not tested). The Smart TV app has no push registration, so it is not affected. The key inside upstream's plugin file is not to be taken out and reused.
- A failed `-Publish` after `gh` created the release but not the asset leaves a half-made release that blocks a retry (releases are never replaced): delete that release by hand, or raise `MoonfinForkRevision`.

## Client defaults for the TV app (stage 2, released as 2.4.0.2 on 2026-10-25, tag `fork-v2.4.0.2`, built from `main` 83f2d59; the editor fix for the two text settings followed as 2.4.0.3, tag `fork-v2.4.0.3`, built from `main` 806f3ba)

The plugin's admin defaults (`PluginConfiguration.DefaultUserSettings`, a `MoonfinSettingsProfile`) are the third layer the TV app resolves, after the device profile (`tv`) and the user's global one. The user wants them to hold a default for every setting the TV app has. The TV chat's list of the app's settings is `local/client-settings.json` (not tracked; per key: the name the app sends, type, label, options, the value Moonfin ships and the one the user chose).

- **How:** typed fields, decided with the user on 2026-10-25. The profile's merge, resolve, storage and apply-to-user code loops over its properties by reflection, so a setting is one nullable property named as the app sends it (`[JsonPropertyName]`, camelCase). 102 were added in `Models/MoonfinSettingsProfile.cs`; of the app's 338 keys, 218 already had a property (the profile has more properties than the app uses, so the totals differ) (and `videoStartDelay` went from `int?` to `double?`, because the app's slider moves in halves; a whole number is still written as `2`, so only a fractional value, which only the TV app or the new tab can set, would trouble a client that reads the field as an integer, and old values read as before; do not set a fractional start delay if the server may go back to upstream's plugin, whose `int?` could not read it). Not added, by the user's decision: eleven account-state keys of the app (`pinCode`, `pinCodeHash`, `pinFailedAttempts`, `pinLockedUntil`, `kidsModeEnabled`, `kidsPinHash`, `kidsPinFailedAttempts`, `kidsPinLockedUntil`, `autoLoginServerId`, `autoLoginUserId`, `syncProfile`): PIN hashes, lockout counters and login ids stay on the device. Three more device security switches were kept out the same way when the review raised them: `allowInsecureCerts` (a default could turn certificate checking off on every device), `pinCodeProtection` (a default could require a PIN nobody set) and `useMoonfinPlugin` (the switch that makes a device use the plugin at all). `ClientDefaultsTests` fails if any of the fourteen appears in the profile or the tab. `autoLoginBehavior` (the user changed it, wants `disabled`) and `alwaysAuthenticate` stay in on purpose: unlike those three they only change sign-in convenience, they cannot switch a security check off or lock anyone out. The same goes for `screensaverAgeFilter` and `screensaverMaxRating` (the screensaver's age-rating guard): they are settable defaults, and applying defaults to users pushes whatever is set, including to children's accounts, so leave all of these *Not set* unless a change is meant. `homeRows` needs nothing: the app converts it to the existing `homeSections` and `homeRowOrder`. The plugin's camelCase names are the contract (the app's `DetailMetadataOrderTv` style capitals were its mistake and are removed there).
- **Editor:** on the Moonbase page, tab *User defaults*, subtab *All TV app settings*. It is drawn from `CLIENT_DEFAULTS_SCHEMA` inside `Pages/configPage.html` (key, type, group, label, options, range) and covers the 131 settings that have no control in the other subtabs; settings that already have a control are not repeated there, so two controls never write one value. *Not set* means null, which leaves the user's own choice (a dropdown choice whose own value is empty, such as "Default" on the accent colors, is a real choice and not the same as *Not set*). The number inputs carry no min or max (and step is "any"), because the browser would refuse to submit the whole page over one value; the range is printed as text and a value you typed outside it is moved to the nearest end when saved (the box then shows that value), while a stored value you did not touch is saved exactly as it was. Groups are collapsible like the other subtabs, and the page's settings search finds the fields (it looks them up on each keystroke, since this tab is drawn after the search is set up). Text boxes are trimmed, an empty choice on a number or yes/no dropdown means not set, and a saved value that no choice matches, even an empty one, is kept as a "(current)" choice rather than cleared. HDR subtitle settings carry "(HDR)" in their label. A number box holding text the browser rejects keeps the stored value instead of clearing it. A list is one entry per line and an empty list means not set. The schema and the 102 properties were generated from the TV chat's list by `local/gen-client-defaults.js` and `local/patch-page.js` (untracked, one-off); a new setting later is a new property plus a line in the schema, and `ClientDefaultsTests` fails when the schema and the profile disagree (missing key, wrong type, a key also controlled elsewhere, an account-state key).
- **Strict types:** the new properties are typed from the app's own values on 2026-10-25 (checked against the list: no mismatch). A client that later sends one of the 102 keys as another JSON type (a number as text, a list as one string) makes that whole profile fail to read, which is how the existing properties behave too; there is no tolerant converter.
- **Types follow the plugin:** a setting the plugin already had keeps the plugin's type in the editor. `maxBitrate` and `screensaverTimeout` are strings in the plugin, in the forms the clients write, and the two clients differ. The TV app writes the bitrate as Mbps text with `"0"` for Auto (`"120"`, `"80"`, `"60"`, ...; it cannot read `"auto"`) and the timeout as `m<minutes>` or `s<seconds>` (`"m5"`, `"s90"`); Moonfin-Core writes `"auto"` for Auto and only `m<minutes>` (`m1`, `m2`, `m3`, `m5`, `m10`, `m15`, `m30`), and ignores the `s` codes (read on 2026-10-25 from Moonfin-Core `main`: `lib/ui/screens/settings/panel/quality_decoding_screen.dart` and `lib/preference/preference_constants.dart`; the TV app's side is `SettingsContext.js`, `bitrateFromServer` and `timeoutFromServer`, which also read any `m<minutes>`; nothing in this repository checks the other app, so if it changes, these labels go stale). The editor therefore offers the forms of both, labelled `(TV app)`, `(Moonfin app)` or `only`, and `ClientDefaultsTests` pins the lists. The choices are the union of both apps' lists (the bitrate has 200, 120, 80, 60, 40, 20, 10, 5, 2 and 1 Mbps), and how Moonfin-Core reads a stored `"0"` was not checked, so for a Moonfin-app user prefer `"auto"`. The user's own profiles hold `"120"` and `"m5"`, which both read. The first version of the editor (2.4.0.2) offered plain digits (`"120000000"`, `"30"`), which only the TV app happens to read; that is fixed in 2.4.0.3; a value saved from the 2.4.0.2 editor shows as "(current)" until it is changed by hand. A default of `"auto"` or `"s90"` is read by only one of the two apps. Every new number is a `double?`, so a decimal from the app can never make a whole profile fail to read (an `int?` would); the editor still rounds the ones whose choices are whole numbers.
- **No new routes:** the defaults are read and written with the plugin configuration (`GET`/`POST /Plugins/<guid>/Configuration`, key `DefaultUserSettings`), and applied to one user with the existing `POST Moonfin/Admin/PushDefaults/{userId}?overwrite=false|true` (admin only). `overwrite=false` merges the defaults into the user's global profile: every setting the defaults have a value for replaces the user's, everything else and the device profiles stay. `overwrite=true` resets the user to a clean global-only profile equal to the defaults, which drops their other settings and device profiles, so copy their settings first. Saving the Moonbase page keeps the values of settings it has no control for, because it edits the configuration it loaded.
